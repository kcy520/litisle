## 〇、全景图：AI 模块处在两条业务线上

**第一条线：机审（判定型 AI，无状态）**

```
内容产生（发布文章 / 上传配图 / 发评论 / 发私信 / 注册取名）
  → 宿主服务本地同步闸门（敏感词，毫秒级；命中高危直接拒绝）
  → 异步送审队列（内容只带定位键，正文/图片由审核侧回查）
  → AI 服务：文本判定 / 图片判定 → 三档结论（通过 / 违规 / 存疑）
  → 通过 → 内容自动放行上线
  → 违规 → 驳回或下架 + 处罚记账 + 通知作者（可申诉）
  → 存疑 → 进入人工复核队列，审核员带 AI 证据裁决
  → AI 不可用 → 保留「审核中」，延迟重试，耗尽转人工（绝不默认放行）
```

**第二条线：生成式（创作辅助，有状态）**

```
作者写作 → 摘要 / 标签建议 / 润色与结构建议 → 作者确认后采用（AI 不直接改稿）
读者提问 → 站内知识库检索 → 带引用的回答 → 引用内容下架后即时失效
审核员 → 判定辅助（风险等级 + 理由 + 是否建议免审）
```

两条线共享同一套底层 AI 供给（模型通道、配额、审计），但**业务后果完全不同**：机审的结论会直接影响内容是否可见，生成式的结论只作为建议呈现给作者或审核员。

## 一、模块定位与职责边界

### 1.1 要解决的问题

| 编号 | 现状问题 | 业务后果 | AI 模块的回应 |
| --- | --- | --- | --- |
| P1 | 机审能力靠 provider 配置占位，文本通道没有提供方、图片模型缺文件 | 审核链路名义上开着，实际所有内容都落到人工；发布后长期「审核中」 | 提供稳定的判定能力，并明确「不可用时的兜底路径」，让机审真正承担分流 |
| P2 | 模型能力分散在各个业务模块，各自接模型、各自写提示词 | 判定口径漂移、换模型要改多处、成本无法统一计量 | 统一收口模型接入与判定口径，业务模块只表达「要判什么」 |
| P3 | 生成式能力（摘要、标签、润色）没有统一入口与配额 | 要么不做，要么各模块各接一套，成本失控、内容不可追溯 | 统一能力出口 + 统一配额 + 统一留痕 |
| P4 | 敏感内容是否出站、留存多久没有明确边界 | 合规风险与舆情风险不可控 | 把「哪些内容允许发给外部模型」做成明确的业务规则 |

### 1.2 负责什么、不负责什么

| 负责 | 不负责 |
| --- | --- |
| 接收「待判定内容」并给出结构化结论（通过 / 违规 / 存疑 + 类目 + 理由） | 内容本身的存储、编辑、上下架（归 content / file） |
| 提供生成式能力：摘要、标签建议、润色与结构建议、站内问答 | 决定内容是否最终可见、是否处罚、是否封禁（归 review 与人审） |
| 模型选型、切换、灰度与效果评估 | 维护敏感词库与词闸门（归 review 的词库治理域） |
| 配额、成本计量、调用留痕、内容出站边界 | 举报受理、申诉裁决、处罚记账（归 review） |
| RAG 检索与引用呈现（知识库载体由 search 提供） | 知识库的摄入、切片与索引维护（归 search） |

### 1.3 与各模块的功能切分

| 模块 | 在审核/生成链路中的功能职责 | 与 AI 的交接物 |
| --- | --- | --- |
| content | 发布编排、状态机、结果回写、生成结果的采用与落库 | 交给 AI：标题+正文、配图清单、文章元数据（经 review 编排送审）；AI 交回：**经 review 转发的判定结论事件**、摘要/标签建议（生成侧直接回交） |
| file | 图片与文件的归属、隔离、恢复、清理 | 交给 AI：图片字节（按 fileId 回查）；AI 交回：图片判定结论（AI→review→file，file 只执行隔离/恢复/清理） |
| review | 词闸门、机审编排、三分态落库、人审队列、处罚、申诉、兜底清扫 | 交给 AI：单次判定请求；AI 交回：判定结论与证据；review 决定后续处置 |
| search | 全文检索、相似推荐、RAG 知识库摄入（切片+向量） | 交给 AI：检索候选与引用元数据；AI 交回：问答与引用展示 |
| auth / user | 注册取名、登录态、封禁下线 | 交给 AI：用户名判定；AI 交回：结论（用户名场景不做自动处罚） |
| notification | 按 review 结论事件触达作者（站内信/邮件等渠道与模板） | 交给 AI：无直接交接；AI 只提供判定理由摘要，由 review 转交（见 §15.6 第 3 条） |

> **结论交接是链式，不是广播**：判定结论的唯一接收方是 review；content / file / search / auth 收到的都是 review 转发的事件，不由 AI 直接写。生成式建议（摘要/标签/润色）不经 review，由 AI 直接回交调用方。

**一句话边界**：AI 只回答「这条内容像什么、风险多高、能不能给建议」，**不决定内容命运**；命运的裁决权始终在 review（机器分流 + 人工终裁）与 content（状态机落库）。

### 1.4 为什么独立成模块，而不是塞进 review

| 理由 | 说明 |
| --- | --- |
| 能力复用面超出审核域 | 摘要、标签、润色、问答的调用方是 content 与读者前台，不属于 review 职责；塞进 review 会让内容侧依赖审核服务可用性 |
| 供给与裁决必须分开演进 | 模型换版、灰度、成本优化属于「供给」；处罚、申诉、人审属于「治理」。混在一起会导致换模型连带改动治理逻辑 |
| 成本与配额需要一个统一主体 | 生成式按用户计量（VIP/普通），机审按内容计量；只有独立服务能同时管住两条线的预算 |
| 合规边界需要单一出口 | 「哪些内容可以出站」必须在一处强制，而不是每个调用方各自判断 |
| 可用性等级不同 | 生成式可以降级为「稍后再试」；机审必须「不通过就不放行」。独立部署才能分别设定容量与降级策略 |

## 二、角色与使用场景

| 角色 | 场景 | 期望结果 | 触发方式 |
| --- | --- | --- | --- |
| 内容作者 | 发布文章、上传配图、编辑已发布内容 | 尽快知道「已发布 / 审核中 / 被驳回」，驳回能看懂理由并申诉 | 发布或上传动作后自动触发 |
| 内容作者 | 写摘要、选标签、改结构、润色 | 一键得到可用的建议，自己确认后才写入稿件 | 作者主动点击 |
| 审核员 | 处理机器拿不准的内容 | 打开任务就看到风险等级、命中位置、判定理由，减少盲看全文 | 任务进入人工队列时自动附带 |
| 审核员 / 运营 | 评估模型是否值得信任 | 能看到自动通过与人工改判的差异趋势，据此调整阈值或换模型 | 后台报表 |
| 普通读者 | 阅读文章、向站内助手提问 | 摘要可读、标签准确、问答有出处且点得开 | 阅读或提问时触发 |
| 运营 / 管理员 | 管控成本与合规 | 能按用户/场景看到用量与花费，能一键收紧或停用某类能力 | 后台配置与报表 |
| 系统（其他模块） | 需要判定或生成 | 拿到结构化结果或明确的「暂不可用」，不拿到似是而非的默认值 | 内部调用 |

### 3.2 分批说明

**第一批（P0）：先让审核链路真正跑起来。**

这一批不追求「判得多准」，而追求「有结论、有兜底、可追溯」。原因很直接：当前机审没有提供方，全部内容转人工，审核时效与人力都被击穿；先把判定能力接上，才能谈准确率与成本。首期判定取向按 D1 定为保守（高召回），以人工产能为约束，自动通过率只在标注数据与评估达标后放宽。

- F1 文本机审：覆盖文章正文、评论、私信、用户名四类场景。文章按段落切片判定，**任一片违规即整篇违规**；用户名场景只留痕、不做自动处罚。私信按 V3 定档（2026-11-08）只做机器判定，不因场景豁免；未公开内容按公开内容处理，前提是法务书面确认（见 §5.4）。
- F2 图片机审：覆盖正文配图、封面、头像。违规图片进入隔离（内容侧不可见），申诉成功后恢复。
- F3 判定辅助：不替代审核员，只把「机器怎么想的」摆到审核员面前，降低单条裁决耗时。

**第二批（P1）：生成式能力，但必须「建议不代笔」。**

- F4/F5/F6 的共同业务约束：AI 产出默认**不落库、不展示**，必须经作者确认；标签不得自动创建新标签，只能从现有标签池中选择（防止标签体系被模型污染）；作者手动新建标签走正常创建流程并过同一道闸门，与本约束不冲突（见 F15）。
- 这一批可以先只对作者开放，读者侧不展示，便于控制成本与质量。

**第三批（P2）：问答与引用，依赖知识库就绪。**

- F7 的前提是 search 侧的知识库摄入可用（公开、过审、足够长的文章才能入库），且引用必须可溯源、下架即失效。
- F8/F9 属于增强能力与会话治理，放在最后。

### 3.3 每个功能的「不做什么」

| 功能 | 明确不做 |
| --- | --- |
| F1/F2 | 不直接改内容状态、不发处罚、不做封禁；不把模型原始输出透给用户 |
| F3 | 不自动裁决，不替代人工；不建议「免审」以外的处置动作 |
| F4/F5/F6 | 不自动改稿、不自动建标签、不自动发布 |
| F7 | 不引用未公开/未过审/已下架内容；不把站内内容当可信指令执行 |
| F8 | 不输出对作者的负面评价性结论，只做结构性分析 |

## 四、业务流程与状态

### 4.1 文本机审流程（文章 / 评论 / 私信 / 用户名）

```
作者提交内容
  → 宿主服务同步词闸门：命中高危词 → 直接拒绝（用户立即看到驳回原因）
                         命中观察词 → 放行但留痕
  → 未命中 → 内容进入「审核中」，作者立即拿到回执（发布动作不等待审核）
  → 审核侧异步取内容 → 调用 AI 文本判定
      ├─ 通过   → 通知业务方放行 → 内容上线
      ├─ 违规   → 通知业务方驳回/下架 → 处罚记账 → 通知作者（附理由，可申诉）
      └─ 存疑   → 进人工复核队列 → 审核员裁决
  → AI 超时/限流/不可用 → 保持「审核中」→ 延迟重试 → 耗尽转人工
```

要点：

- **用户不会被「审核中」卡住发布动作**，但内容可见性取决于结论。
- 待审期间内容发生变化（如作者撤回后修改再提交），若结论迟到且内容指纹已变化，旧结论直接丢弃（防「改完稿却被旧结论下架」）；已发布内容 `status=2` 时禁改正文/标题/配图，不存在「已发布反复送审」路径（见 §十二 第 1 条）。
- 用户名场景同步拦截优先，异步结论只用于留痕与治理，不产生处罚。
- **首期判定取向（D1，已定 2026-11-08）**：以高召回为主，宁可多转人工；自动通过率随标注数据与准确率评估逐步放宽。

### 4.2 图片机审流程

```
图片上传（配图/封面/头像）
  → 归属与用途校验（只能引用本人文件、用途必须匹配）
  → 查复用：命中黑名单 → 直接拒传；命中有效 PASS 结论（键与有效期见 F12）→ 直落「通过」，不送审
  → 未命中 → 送审 → AI 图片判定
      ├─ 通过 → 正常展示
      ├─ 违规 → 图片隔离（业务侧不可见）+ 记入短期拒传名单
      └─ 存疑 → 人工复核；复核前不展示
  → 申诉成功 → 解除隔离 + 移出拒传名单
  → 到期清理：长期违规且无待处理申诉的隔离图片，超过保留期后软删（可恢复期内可人工恢复）
```

要点：

- **免文不免图**：文章正文即便命中免审，配图仍必须复审。
- **首期图片判定范围（D2，已定 2026-11-08）**：只在本地/私有化模型内处理，不外发 UGC 图片；本地模型不可用时保持「待审 + 全量转人工」，不以云 API 兜底。
- 隔离期默认 10 天（可配置），期间申诉中的图片不清理。
- 缓存/黑名单命中同样要留痕；复用键与有效期见 F12，不得为省调用跳过记录。

### 4.3 结论与用户可见结果

| 机审结论 | 内容状态 | 作者看到什么 | 读者看到什么 | 可否申诉 |
| --- | --- | --- | --- | --- |
| 通过 | 首发：审核中 → 已发布；复审：维持上线 | 「已发布」 | 正常可见 | 不适用 |
| 违规 | 首发：驳回；复审：下架 | 「未通过审核」+ 风险类目与理由 + 申诉入口 | 不可见 | 可以 |
| 存疑 | 保持审核中，进入人工队列 | 「审核中，预计…」 | 不可见 | 结论出来后可申诉 |
| AI 不可用 / 重试中 | 保持审核中 | 「审核中」 | 不可见 | 结论出来后可申诉 |
| 词闸门直接拒绝 | 未进入发布流程 | 立即看到驳回原因 | 不可见 | 可走误报反馈入口 |

### 4.4 人工复核如何介入

| 介入原因 | 进入方式 | 审核员看到什么 | 收口方式 |
| --- | --- | --- | --- |
| 机审存疑 | 自动进人工队列 | 风险等级、命中位置、AI 理由、原文/证据图 | 认领后裁决：通过 / 驳回 / 处罚 |
| 机审重试耗尽 | 自动转人工（绝不自动放行） | 同上 + 「机审未完成」标记 | 同上 |
| 用户举报 | 举报初审分流后进队列 | 举报理由 + 证据 + 机审证据 | 同上 |
| 审核员认领后超时未处理 | 定时回收进池 | 任务重新可认领 | 重新认领 |
| 任务进池后 T 小时无人认领 | 升级告警并派单给值班主管（T=4 小时，V4 定档 2026-11-08） | 无 | 主管指派或回收重排 |
| 申诉超时无人裁决 | 定时按「维持原判」收口 | 无 | 通知作者 |

> 申诉期间的状态：内容保持原状态（违规则维持驳回/下架），隔离图片不清理；申诉只改变「是否改判」，不把内容提前恢复为可见。裁决沿用 §5.1 的 7 天时限，超时按维持原判收口。

### 4.5 异常与降级时，用户侧看到什么

| 异常 | 业务处理 | 用户侧表现 | 是否可能漏审 |
| --- | --- | --- | --- |
| AI 超时 | 延迟重试 | 保持「审核中」，结果晚出 | 否 |
| AI 限流 / 瞬时配额不足 | 延迟重试，不丢内容（与「当天预算打满」区分，见下行） | 保持「审核中」 | 否 |
| 当天预算打满（D15） | 立即转人工并告警，不自动重试；机审预算优先，不因生成超支停用机审 | 保持「审核中」，转人工后出结论 | 否 |
| AI 服务整体不可用 | 重试耗尽转人工；同一用途连续失败达 5 次（5 分钟窗口，V5）打开服务级熔断，期间新任务不再逐条重试、直接转人工 | 保持「审核中」，转人工后出结论 | 否 |
| 模型未配置 / 模型文件缺失 | 按「确定不可用」处理，启动即告警；自检判不可用时直接转人工，不走单条 5 次重试；自检恢复后自动切回 | 保持「审核中」，全量转人工 | 否（但人力被打穿） |
| 降级恢复（模型/外部服务恢复） | 自检通过后切回；在途任务继续原重试序列；降级期间产生的结论打 `degraded=true` 标记 | 无变化 | 否 |
| 生成式调用失败 | 最多重试 1 次；仍失败则本次终态为「未生成」，退还已预扣配额 | 看到「暂时无法生成」，可手动填写 | 不适用 |
| 知识库不可用 | 降级为不引用回答，并显著标注「未引用站内内容」；事实性问题只答「暂无相关资料」，不猜测 | 回答没有引用卡片，且带有未引用提示 | 不适用 |

> 降级期结论：标 `degraded=true` 的结论正常参与本次分流，但不计入 F13 的效果评估样本，也不作为 F19 重判的对比基线；降级恢复后，在途任务继续，不重新从头判定。

> 红线：**任何情况下都不能因为 AI 不可用而默认放行**。宁可显示「审核中」并转人工，也不放大风险内容。

### 4.6 生成式流程（摘要 / 标签 / 问答）

```
作者点击「生成摘要」→ 取当前稿内容 → AI 生成 → 以建议态展示
  → 作者编辑或确认 → 写入稿件（记一次「采用」）
  → 未确认则丢弃，不落库

读者提问 → 判断是否需要查站内知识库 → 检索公开且过审的文章片段
  → 组回答 → 附引用卡片（标题/作者/链接 + 文章版本）
  → 回答展示前校验：文章当前仍可见；且引用所依据的切片构建版本与文章当前版本一致
      ├─ 已下架 → 去掉该引用或整段降级
      ├─ 仅元数据更新（标题/标签/摘要）→ 允许展示，但标注「内容已更新」
      └─ 正文已改而切片未重建 → 移除该引用（search 的 article-updated 只更新元数据、不动 chunks）
```

> **引用一致性（见清单索引 Q75）**：引用返回必须带「文章版本 + 切片构建版本」，AI 侧展示前做一次比对；两者不一致说明正文已变而向量未重建，此时不得把旧切片当作现行正文引用，只能移除或标注。下架失效与改稿失效是两条独立防线，不能互相替代。

## 五、业务规则与约束

### 5.1 审核时效

| 环节 | 内部目标基线（D7 已定：对外只显示状态 + 预计范围，不承诺具体时长） | 超时后的行为 |
| --- | --- | --- |
| 同步词闸门 | 毫秒级，用户无感 | 不适用 |
| 文本机审 | 95% 在 60 秒内出结论 | 继续重试，内容保持审核中 |
| 图片机审 | 95% 在 60 秒内出结论 | 同上 |
| 人工复核 | 95% 在 24 小时内裁决 | 队列告警 + 运营介入 |
| 申诉 | 7 天内裁决，超时按维持原判 | 自动收口并通知作者 |

> 申诉恢复时效：裁决落库后 30 分钟内完成解隔离与恢复可见（不含 7 天裁决等待期）；§七 F2 验收的「30 分钟」即指这一段。
>
> 60 秒计时口径：从任务入队到首次结论产出（含首次重试的等待）；含全部重试的端到端另设 P95 指标（见 §七 与 [AI-Architecture.md](../Architecture/AI-Architecture.md) 的可观测性一节），不并入本条。
>
> 首期按 D1 保守取向，存疑转人工比例会高于后期；24 小时是人力可承载时的目标，人力不足时以队列积压告警与入口限流优先，不对用户承诺固定时长（与 D7 的建议取向一致）。

### 5.2 失败重试对用户的影响

- 机审失败后按指数退避重试，最多 5 次（约 15 分钟量级），期间用户始终看到「审核中」。
- 模型或服务经自检判定为「确定不可用」时，不再逐条重试，直接转人工并带「机审未完成」标记，避免每条白等约 15 分钟并持续无效调用；自检恢复后自动切回。
- 重试耗尽后进死信并转人工，**不会出现「既不在队列也没结论」的悬空内容**。
- 对用户的影响是**延迟**，不是**放行**：不会出现「因为机器坏了所以违规内容上线」。

### 5.3 成本与配额

| 约束 | 规则 |
| --- | --- |
| 机审调用量 | 入口限流（控制内容进入速度）+ 模型调用限流（控制真实调用花费）两层独立计数，互不挤占 |
| 重复判定成本 | 内容未变且上次结论为终局时复用结论；**复用键统一定义见 F12 业务规则**（文本含模型/提示词/词库三版本 + 场景 + 指纹；图片含模型版本 + 指纹），换版不复用；免审有效期 72 小时，口径见 F12 |
| 生成式配额 | **已定（D5，2026-11-08）**：普通用户先按日低配额，按用户等级逐级放开；VIP 设高额度上限，不设「不限量」；配额与**生成预算科目**挂钩（机审预算独立且优先，见 D15），超限提示「今日额度已用完」 |
| 会话留存 | **已定（D6、D25，2026-11-08）**：留存期与生成内容同为 90 天；90 天内最多保留 200 个会话，单会话最多 500 条消息，超出按「最久未活跃」淘汰。天数到期与条数/消息数超限是「与」关系，任一先触发即淘汰 |
| 成本可见 | 按用途（机审文本/机审图片/摘要/标签/问答）与按用户可查用量与花费；**该五类为计量打标的唯一定义**，D15 的「机审」是「机审文本 + 机审图片」的合称，不另立枚举 |

**生成式配额与预算参数（见清单索引 Q39）**：D5 定了机制（按日次数 + 等级 + 生成预算分账）；预算如何分、谁优先以 D15 为准——机审预算独立、生成预算打满只停生成，不做全局熔断。具体数值已按 V8 定档（2026-11-08），见下表与 §16.3。其中「DAU 15%」是待校准初值，不是对外承诺。

| 参数 | 用途 | 选定值（V8，2026-11-08） |
| --- | --- | --- |
| 普通用户日生成次数 | 单用户日上限，超额提示「今日额度已用完」 | 10 次/日 |
| 用户等级系数 | 按等级逐级放开倍数 | 1×/2×/3×（10/20/30 次） |
| VIP 额度上限 | 高额度但非不限量 | 60 次/日 |
| 生成式日预算 / 月预算 | 触发 80% 预警与 100% 停生成 | 日预算＝DAU×15%（初值待校准）×10 次×单次成本；80% 预警、100% 停生成 |
| 机审预算额度 | 独立科目，打满转全量人工并告警 | 不设单用户上限，按量独立核算 |

### 5.4 数据留存与合规

| 对象 | 留存建议 | 说明 |
| --- | --- | --- |
| 机审结论与证据 | 不少于 6 个月（合规留存期），超期归档 | 证据 = 原因码 + 命中规则 + 置信度 + 内容指纹 + 模型/词库/提示词三版本号 + 结论时间；**不含模型原始返回全文**（D14）；现有归档任务默认关闭，需随本模块启用 |
| 图片隔离 | 默认 10 天，申诉中的顺延 | 软删后仍有恢复期（**7 天**，与 File 文档一致），期满物理删除 |
| 生成式输入输出 | **已定 90 天（D6，2026-11-08）**；「可配置」只指清理任务的执行时间，不改留存期；支持用户删除 | 删除执行方：AI 受理请求并按对象分派——会话与生成记录由 AI 清理，正文/配图由 AI 发指令给 content/file 执行；异步任务 + 回执 + 审计，AI 不直接删存储对象 |
| 模型调用留痕 | 记录调用方、场景、耗时、结论、模型版本，不记录完整正文 | 便于追溯与成本核算，降低敏感内容散落 |

**结论举证（D14 补充）**：常规举证依赖结论记录本身（原因码、命中规则、置信度、内容指纹、模型/词库/提示词三版本）；需要复现判定时用固定评测集重跑。若模型版本已下线、评测集已变更导致无法重跑，则以「结论记录 + 发布时的评测报告 + 当次人工复核记录」组成证据包，重跑不作为唯一举证方式。

**内容出站边界（V3 已定档，2026-11-08；原 Q63 关闭）**：

- **私信内容只做机器判定**：不因「私信」场景而豁免机审；发送前按下方脱敏规则处理。
- **未公开内容按公开内容处理**：草稿、审核中、仅自己可见的内容与外发同等对待，不再作为「禁止外发」类别。
- 用户主动删除的内容仍**不外发**（已删除内容失去处理必要性）。
- **UGC 图片首期不外发**：D2 不变，只在本地或私有部署模型处理；外部云 API 需先满足合规评估、脱敏与显式开启。
- 最小必要原则：优先片段/摘要而非全文；先脱敏后外发；禁止附带用户身份信息。
- 任何外发通道都必须可审计（哪条内容、何时、发往哪家）。
- **前提假设（不是默认成立）**：需法务**书面确认**三项——①未公开内容与私信可外发；②脱敏字段清单与口径（见下表）；③用户告知与同意文案及入口位置。**未取得法务书面确认前，本项按待确认处理**：私信与未公开内容只走本地模型或转人工，不得接入外部通道。
- **翻案条件**：法务否定该口径，或监管要求发生变化（如新增数据出境、个人信息保护限制）时，回退为「未公开内容与私信不外发、全量转人工」，并同步调整 V6 抽样范围。

**脱敏的可执行规则（见清单索引 Q65）**：

| 项 | 规则 |
| --- | --- |
| 执行方 | 统一在 AI 调用入口的「出站过滤器」执行；调用方不各自脱敏，避免同一内容两条通道两种处理 |
| 必须脱敏（替换为占位符后再外发） | 手机号、邮箱、身份证号、银行卡号、精确门牌地址、GPS/精确地理位置、IP、设备号、用户名/昵称、头像链接、私信双方标识、外部链接（含短链与带参 URL，可能夹带 uid/token）；时间粗化到日 |
| 可直接不发送（脱敏也不发） | 用户已删除内容、含身份直链的截图、脱敏后仍无法排除身份指向的长文本；此类内容命中即整条不外发，转本地/人工 |
| 任何场景都不外发 | 密码、Token、密钥类字段；出现即阻断并告警 |
| 用户告知与同意 | 入口固定两处：①注册或首次使用 AI 服务时的《AI 处理说明》勾选；②发布内容、发送私信前的提示条（可展开全文）。条款须写明「未公开内容与私信会发送至外部模型做安全判定」；用户可在设置中查看，撤回只影响未来数据，已产出结论按留存期管理 |
| 校验与留痕 | 出站前做字段白名单 + 正则双校验，未脱敏字段命中即阻断并告警；日志只记内容指纹与命中类型，不记原文 |
| 审计抽样 | 对已外发请求做人工抽样复核：每月 50 条，或按 1% 取大者（V6）；**覆盖文本机审全量外发（含私信、未公开内容）与生成式、问答外发** |

### 5.5 内容安全红线

1. 机审不可用不默认放行。
2. 模型原始输出不直接展示给终端用户，只展示结构化、可解释的结论。
3. 生成式内容必须标注为 AI 生成/建议，作者确认后才进入正文。
4. 标签建议不得自动创建新标签。
5. 问答引用必须可溯源，且引用内容下架后即时失效。
6. AI 不得代替人工做出封禁类处置。

**AI 标识的生命期（见清单索引 Q64）**：生成内容被作者采用后即转为正式内容，AI 标识按 D3/D13 随正文持续展示，直至内容删除；采用后的正文与配图按 content 的留存与删除规则处理，AI 会话侧的副本仍按 90 天清理，两者互不替代。

> 「AI 不跨库直写业务表」与 F21 补偿不矛盾：F21 属于 review 的兜底能力，补偿也是向 content / file 发指令，由对方执行并回执。

## 七、验收口径（业务可观察、可验证）

> 以下阈值为验收基线，已随 D1 / D2 定档（2026-11-08），不再另行拍板；需要调整时按翻案流程改 §十六。验收不看「代码是否写完」，只看「业务现象是否改变」。

| 编号 | 功能 | 验收标准（业务可观察） | 验证方式 |
| --- | --- | --- | --- |
| F1 | 文本机审 | **按 D1 保守取向验收**：抽检 100 篇，机审在 60 秒内给出「通过/违规/存疑」结论的比例 ≥95%；存疑比例与人工日产能匹配——判定口径为「连续 3 天队列积压 > 50 条或平均等待 > 6 小时即不达标」（V11 定档，X 与 review 现配置同值）；**不以自动通过率作为首期达标条件**；抽检漏放为 0 | 后台看板 + 抽样对照人工复判 + 队列积压监控 |
| F2 | 图片机审 | **按 D2 首期口径验收**：仅本地/私有化模型参与判定；违规图片在展示前被隔离，抽检 100 张违规样本漏放为 0；申诉成功后 30 分钟内恢复可见；本地模型不可用时全量转人工且不视为漏放 | 造样本测试 + 申诉走查 + 不可用演练 |

| F17 | 非图片多模态检测 | 不适用：本期排除（D10、D11），不设验收 | — |
| F18 | 发布入口全覆盖与送审守卫 | 入口清单逐项抽测各 1 次，均产生送审记录；绕过入口被拦截并给出补送审提示 | 入口清单走查 |
| F19 | 存量结论重判与版本迁移 | 换版后可查「旧版本结论」占比；同内容同版本的重判任务不重复；过期结论不参与复用但仍可举证 | 版本演练 + 任务去重核对 |

| F21 | 对账与卡死任务清扫 | 演练中人为丢失一路结论，可在对账周期内补齐或转人工，不出现「既不在队列也无结论」；积压与 DLQ 告警可在演练中触发 | 故障注入 + 告警演练 |
| F22 | 生成质量评测与人工抽检 | 每版本评测集 ≥300 条（D21）；报告含场景级准确率与错误分类；「是否具备自动写入条件」有数据支撑 | 评测报告评审 |

**全模块通用验收**：

- AI 完全不可用时，内容不会放行，审核链路不静默失败。验收方式：演练中停用图片模型，1 分钟内产生告警，值班人员 5 分钟内按 Runbook 确认「哪一类能力不可用」并完成处置；无 Runbook 或超时确认视为未通过。
- 任一模型换版后，旧结论不复用；可通过「同一批样本在新旧版本下的判定差异」评估是否值得切换。

**可以先做、不依赖外部模型的部分**（建议优先启动，避免被模型接入阻塞）：

1. 阶段 0 的「不可用显式化 + 告警 + 看板」：把当前「全量转人工」从隐性事实变成可见状态。

4. 内容出站边界的配置化：先用开关与白名单把边界固定下来，接模型时不用再改业务。

| 编号 | 已定结论 | 前提假设 | 前提不成立时如何调整 |

## 十、补充：场景与结论消费矩阵

> 本章按最新模块文档补记（2026-11-08）。同一套 AI 判定能力，在不同业务场景里的「谁送审、谁消费结论、用户看到什么」并不相同，原文档只按文章主链路描述，容易漏掉图片与评论/私信的差异。

**状态码与字段定义（见清单索引 Q30，2026-11-08）**

全文同时用到两套字段，先在此定义，避免码值混用：

| 字段 | 取值 | 含义 | 对外是否可见 |
| --- | --- | --- | --- |
| `content.status` | 0 草稿 / 1 审核中 / 2 已发布 / 3 驳回 / 4 已下架 | 文章生命周期状态（content 维护） | 1、3、4 对作者可见；2 对读者可见 |
| `file.safe_flag` | 0 违规隔离 / 1 通过 / 2 待审 / 3 存疑 | 单个图片/文件的安全状态（file 维护），**与 content.status 无关** | 仅 1 可公开引用；0/2/3 均不可见 |

**允许迁移与推进方（见清单索引 Q30）**

| 字段 | 迁移 | 触发条件 | 推进方（裁决 → 执行） |
| --- | --- | --- | --- |
| content.status | 0 → 1 | 作者提交发布 | content |
| content.status | 1 → 2 | 文本结论通过、配图结论全部通过、处罚态回查通过 | review 裁决 → content 条件更新 |
| content.status | 1 → 3 | 文本或配图结论违规 | review 裁决 → content 条件更新 |
| content.status | 2 → 4 | 复审违规，或封禁连带下架 | review 裁决 → content 条件更新 |
| content.status | 3 → 1 | 作者修改后重新提交 | content |
| content.status | 4 → 2 | 申诉改判恢复 | review 裁决 → content 执行（含配图解隔离） |
| file.safe_flag | 2 → 1 / 2 → 0 | 图片判定通过 / 违规 | review 落库 → file 执行 |
| file.safe_flag | 2 → 3 | 图片判定存疑 | review 落库 → file 执行 |
| file.safe_flag | 3 → 1 / 3 → 0 | 人审终局通过 / 违规 | review 人审裁决 → file 执行 |
| file.safe_flag | 0 → 1 | 申诉改判 | review 裁决 → file 解隔离 |
| file.safe_flag | 1 → 0 | 复审违规 | review 裁决 → file 隔离 |

> 口径约定：`safe_flag=3` 是「存疑」子态，对外表现与 2 相同（都不可见、待人工），只用于区分「机器拿不准」与「还没判」；不得把 3 当成 2 写回。所有写回必须带期望旧值做 CAS 与结论序号，冲突时记录并丢弃，不得覆盖（序号规则见 F10「先后守卫」）。AI 只产出结论，不直接写这两个字段。

| 场景 | 内容来源 | AI 判定对象 | 结论消费方 | 用户可见结果 | 现状/备注 |
| --- | --- | --- | --- | --- | --- |
| 文章正文（bizType=1，scene=ARTICLE） | content | 标题+正文 | content：与配图结论聚合后 CAS 1→2 / 1→3 / 2→4 | 作者看「审核中 / 已发布 / 驳回」；读者看内容是否可见 | 文本通道当前无提供方，结论落「存疑」转人审 |
| 文章配图复审（scene=ARTICLE_IMG_RE_REVIEW） | content | 整篇配图清单 | file 回写 safe_flag；content 聚合槽 | 审核前配图不展示；违规图隔离 | 免审直落仍发配图复审，按整篇聚合 |
| 独立图片上传（bizType=6，scene=IMAGE） | file | 单张图片（配图/封面/头像） | file：safe_flag=2 待审 → 1 通过 / 0 违规隔离 / 3 存疑 | 上传后暂不可公开引用；违规不可见 | 上传缓存未命中即送审，不等文章发布 |
| 评论（bizType=2，scene=COMMENT） | social | 评论正文 | content 侧仅「挂起留痕」，不驱动评论状态 | 评论是否展示由 social 决定 | social 模块当前未启用 |
| 私信（bizType=5，scene=MESSAGE） | social | 私信正文 | social 消费结论 | 发送方看到发送受限或失败 | social 模块当前未启用 |
| 用户名（bizType=3，scene=USERNAME） | auth / user | 昵称/用户名 | review 仅留痕，不建任务、不处罚 | 同步 DFA 直接拒绝；异步结论只做治理 | 用户名场景不产生处罚 |
| 文章摘要（summary） | content | 摘要文本（≤500 字） | 同步 DFA 闸门；AI 摘要生成后需再过闸 | 作者看到摘要校验/生成建议 | 摘要不参与正文指纹 |

**这张表解决的问题**：原文档 F1 把「文本机审」笼统覆盖文章/评论/私信/用户名，但四类场景的结论落地方式完全不同；尤其图片是「file 先审、content 后聚合」的双层结构，漏掉任一层都会造成「图片已放行、文章却没过审」或反之。

## 十一、补充功能项（F10–F17）

### F10 判定结论处置衔接与申诉恢复

| 项 | 内容 |
| --- | --- |
| 批次/状态 | 第一批 P0（依赖 F1/F2） |
| 输入 | AI 判定结论（通过/违规/存疑 + 类目 + 理由 + 模型版本）；人工裁决；申诉改判结果 |
| 输出 | 带版本标识的结论（供业务方回写）；申诉恢复所需的原判定证据；恢复/隔离的业务依据 |
| 触发时机 | 机审完成；人工裁决；申诉裁决 |
| 可见结果 | 作者看到状态流转；申诉成功后内容与配图恢复；读者看到内容重新可见 |
| 不做什么 | 不解封、不撤销处罚、不跨库直写业务表 |

**业务规则**：

- AI 只产出判定，不直接改内容状态；状态流转由 content/review 条件更新完成。
- 驳回后的恢复只认「申诉改判」来源，不允许机审或人审反向恢复。
- 恢复前必须回查作者处罚权威态：**封禁中不放行；回查异常、业务码非 0、数据为空同样不放行**，进入延迟重试，不得把「查不到」当成「没处罚」。
  - 回查重试设上限：最多 **3 次**、最长 **1 小时**（V1/V2 定档 2026-11-08，两值成对，单改一个会错配）；耗尽后维持驳回，同时在人工队列生成一条「恢复回查失败」复核工单并告警，作者侧显示「复核中」，不得静默卡住。
  - 复核工单只能由人工确认处罚态后收口：确认未处罚则恢复，确认封禁则维持驳回并告知作者。
- 文章恢复需连带解除配图与封面的隔离，并重新发布，保证搜索索引与知识库引用对称恢复。
- 结论事件必须携带内容指纹，供业务方丢弃「内容已改、结论迟到」的陈旧判定。
- **先后守卫（跨事件）**：结论事件还要携带 `裁决时间` 与 `裁决序号`（同一内容单调递增，由 review 落库时分配）。业务方只接受序号不小于「当前已生效最终裁决」的事件；序号更小的迟到事件（典型是申诉改判恢复后迟到的机审违规结论）直接丢弃并写审计日志，不得再次改变内容状态。

### F11 图片复审与隔离治理协同

| 项 | 内容 |
| --- | --- |
| 批次/状态 | 第一批 P0（依赖 F2） |
| 输入 | 上传图片（配图/封面/头像）；文章配图清单；申诉改判 |
| 输出 | safe_flag 语义（待审/通过/违规隔离/存疑待审）；隔离与解隔离的业务指令 |
| 触发时机 | 上传即送审；文章发布或免审直落时配图复审；违规判定；申诉改判 |
| 可见结果 | 审核完成前图片不可公开引用；违规图不可见；申诉成功后恢复 |
| 不做什么 | AI 不移动或删除存储对象、不设定隔离期、不决定是否清理 |

**业务规则**：

- 上传后先落「待审」占位；未出结论前不得公开引用。
- 违规判定触发**物理隔离**（移入隔离前缀），不是只改一个标记位。
- 存疑判定保持待审占位，人审终局前不展示。
- 文章配图复审按整篇配图聚合判定，避免「逐张都通过、整篇却有问题」的漏审。
- 申诉成功解隔离并移回原前缀；维持驳回则保持隔离。
- 到期清理只清「最新结论仍违规 + 无待处理申诉 + 超过保留期」的图片；软删有恢复期，期满才物理删除。
- 短期拒传名单由 file 维护；申诉平反时由 review 在改判事件中下发移除指令，file 执行并回执，否则用户改判后仍传不上图；F21 对账清单纳入「名单已移除」校验。
- **首期判定范围（D2，已定 2026-11-08）**：仅本地/私有化模型参与；本地模型不可用时保持待审并全量转人工，不启用云 API 兜底。
- **两路并发写回（见清单索引 Q58）**：上传预审与配图聚合复审可能同时写同一 `safe_flag`，写回必须带期望旧值 + 结论序号做 CAS（口径同 §十「允许迁移与推进方」）；冲突时聚合复审优先，单张结论记为过程记录不覆盖整篇结论。同一图片内容（sha256 相同）默认共享结论，但必须命中 F12 的「模型版本 + 图片指纹」复用键，未命中则各自判定。

### F12 结论复用供给

> 原名「结论复用与免审供给」。免审不由 AI 决定，改名的原因见下方业务规则；旧称保留在此，便于按旧标题检索。

| 项 | 内容 |
| --- | --- |
| 批次/状态 | 第一批 P0（随 F1/F2 一起具备） |
| 输入 | 历史结论（含模型版本、词库版本、提示词版本）；内容指纹；场景 |
| 输出 | 可复用结论 / 必须重新判定 |
| 触发时机 | 发布前免审判定；送审消费前查重 |
| 可见结果 | 作者无感；换词库或换模型后自动重判 |
| 不做什么 | AI 不判定「是否免审」，也不写免审键（由宿主与 review 判定、写入） |

**业务规则**：

- 只有终局结论（通过/违规）可复用；存疑不缓存。
- **结论复用键（唯一定义处）**：
  - 文本：`模型版本 + 提示词版本 + 词库版本 + 场景 + 内容指纹`。
  - 图片：`模型版本 + 图片指纹`；若图片判定叠加词库或提示词辅助，则相应版本一并纳入。
  - 三类版本号按各自发布单调递增发号，不得用秒级时间戳充当版本（同秒多次变更无法区分）；任一版本变化即旧结论不再参与复用（旧结论仍作历史证据，见 F19）；未携带版本信息的结论不得复用。
  - §5.3「重复判定成本」只引用本键，不再另写一套。
- **免审不归 AI 判**：免审判定由宿主与 review 的 `last-hash` 机制负责，键与有效期以 [Review-Architecture.md](../Architecture/Review-Architecture.md) 的「免审与 last-hash」为准：`review:last-hash:{wordlibVer}:{bizType}:{scene}:{bizId}`，TTL **72 小时**；AI 不写免审键、不另立一套键。
- 免审成立需同时满足「内容指纹未变 + 上次通过 + 当前非驳回态 + last-hash 未过期」；**免文不免图**，配图仍必须复审。
- AI 侧复用结论时仍按上面的复用键二次校验模型/提示词版本：review 的 72 小时免审只覆盖「内容未变 + 词库未变」的短期场景，不等于 AI 结论永久有效。
- 复用命中仍要留痕，不能因为复用省掉审核记录。

### F13 审核反馈闭环与效果评估（已补实，2026-11-08）

| 项 | 内容 |
| --- | --- |
| 批次/状态 | 第一批 P0（采集随人审上线）；评估与回流第二批 P1 |
| 输入 | 审核员对 AI 建议的每次操作；人工最终结论；用户申诉与抽样复核结果；F21 上报的过期任务 |
| 输出 | 逐条反馈记录；场景/版本级采纳率、否决率、误判率；阈值与词库候选集；灰度评估样本；看板与告警 |
| 触发时机 | 每次审核动作实时记录；按日聚合；按周出评估 |
| 可见结果 | 审核员在任务详情看到 AI 建议与理由；负责人看到看板；作者无感 |
| 不做什么 | 不自动训练、不自动调阈值、不自动换模型、不自动改词库、不自动处罚 |

**F13.1 采集点（记什么、在哪记）**

记录时机：审核员在任务详情上每执行一次操作就写一条，包括采纳 AI 建议、否决 AI 建议、改判类别、转他人复核、直接放行；任务超时未处理由 F21 写一条「过期」记录。一条任务允许多条记录，不复用「最终一条」。**过期记录以「任务标识 + 记录类型 = 过期」为唯一键，F21 反复扫描时幂等跳过，不重复写入**，否则会虚增过期数与时效统计。

| 数据项 | 用途 | 必填与说明 |
| --- | --- | --- |
| 记录标识 | 幂等与追溯，同一次操作重复提交不重复计数 | 必填；由服务端按「任务 + 操作类型 + 客户端幂等键」生成，重试复用同键 |
| 任务标识 | 关联 `review_task`，定位排队与耗时 | 必填 |
| 内容标识与业务类型 | 回溯原文/原图；区分文章、图片、评论等 | 必填；只留标识与指纹，不冗余存全文 |
| 场景 | 文本/图片/评论/私信/头像/封面/用户名，用于按场景切分 | 必填 |
| AI 建议结论 | 通过/违规/存疑；违规时记录风险类别 | 必填；无建议时标「无」 |
| AI 置信度 | 判断「存疑」是否合理；低置信度样本优先抽样 | 模型不返回时标「不可用」，不参与置信度分析 |
| 人工最终结论 | 作为准确率分母 | 必填；过期样本留空并标「未处理」 |
| 是否一致 | 计算采纳率、误判率 | 必填；无法比较时标「不可比」 |
| 改判原因标签 | 归因与候选集分组 | 见下方标签集合；**已定（D22）：强制** |
| 模型版本 | 按版本对比效果，支撑灰度与回退 | 必填 |
| 提示词版本 | 定位提示词改动带来的效果变化 | 必填；无提示词的场景标「无」 |
| 阈值版本/词库版本 | 区分「模型问题」与「规则问题」 | 必填 |
| 操作类型 | 采纳/否决/改判/转复核/直接放行/过期 | 必填 |
| 处理耗时 | 评估人工成本与时效 | 必填，单位毫秒 |
| 审核员标识 | 责任追溯与工作量统计 | 默认脱敏存储（化名或哈希），真实身份只在审计日志可查 |
| 时间 | 分时段分析 | 必填 |
| 上一条记录标识 | 多次改判时串成链路 | 改判/复核时必填 |
| 是否最终生效 | 统计以最终生效为准，过程分析用全量 | 每条记录标记，任务关闭时回填 |

原因标签建议集合（单选为主，必要时可多选）：

- **漏判**：AI 判通过，人工判违规
- **误判**：AI 判违规，人工判通过
- **类别错**：结论方向对，但风险类别错
- **边界模糊**：内容处于规则灰区
- **上下文不足**：只看片段无法判断，需全文或前后文
- **规则冲突**：词库与模型结论冲突
- **其他**：以上都不适用，必须填备注

不填处理（已定，D22）：强制选择，无合适项选「其他」并填备注；若允许留空，则该条标记「质量待补」，只进入总量统计，不进入按原因的候选集。

多次改判的口径：全过程保留、不覆盖；**准确率以任务关闭时的最终生效结论为准**，过程指标（转复核率、平均改判次数）用全量记录。用户申诉改判也写一条新记录，理由标签沿用申诉理由映射。

**F13.2 存储（存哪、存多久）**

- 存储类型：新增**追加型反馈记录实体**（暂名 `moderation_feedback_record`），一次操作一条记录，只增不改（「最终生效」标记可回填）。不写 DDL，留给技术设计。
- 与现有表的关系：
  - `moderation_record`：机审提交与原始结论，属输入侧；反馈记录引用其轮次，不复制全量字段。
  - `review_task`：人工任务与状态，属流程侧；反馈记录引用任务标识，任务状态仍以 `review_task` 为准。
  - `punish_log`：处罚流水，属结果侧；仅违规样本关联，无处罚时不强关联。
- 为什么不复用：`moderation_record` 是「一次送审一条」，承载不了同一任务多次改判；`review_task` 是状态表，不适合追加分析数据；混用会让口径互相污染。
- 保留期**已定（D23，2026-11-08）：12 个月**；前 6 个月在线可查，后 6 个月归档只供评估。理由：模型与提示词迭代通常跨季度，6 个月不足以做跨版本对比；与机审留痕 6 个月不一致的说明见 D23。到期后只保留聚合指标与脱敏样本，逐条记录删除。
- 脱敏：审核员标识默认化名；内容只留标识、指纹与必要片段，原文/原图按内容侧留存策略处理。必要片段仅限命中段落，**不超过 200 字**，且不含个人身份信息；能只留指纹 + 偏移定位时优先不存片段。

**训练用途的授权链路（见清单索引 Q66）**：

| 环节 | 规则 |
| --- | --- |
| 授权入口 | 用户设置中的独立开关，默认关闭；不得与注册协议打包默认勾选 |
| 记录字段 | 用户标识、授权时间、用途范围（训练 / 评测集）、授权版本、撤回时间；与反馈记录（F13）分开存，不混用 |
| 范围与期限 | 仅限 D24 允许的用途；期限 2 年、到期重新授权（V12 定档 2026-11-08）；可覆盖的数据范围以授权时勾选为准 |
| 撤回 | 撤回即时生效，停止用于新的训练与评测集构建；已产出模型不追溯，评测集在下一版本剔除该样本（V12；「不追溯」口径需法务书面确认） |
| 未授权/已撤回数据 | 只能用于当次判定与留痕，不得进入训练或评测集 |

**F13.3 消费方（谁看、看什么）**

| 消费方 | 看什么 | 最小样本与频率 | 产出 |
| --- | --- | --- | --- |
| 效果评估 | 场景 × 模型版本 × 提示词版本的采纳率、否决率、误判率、漏判率 | 每个切分格（场景 × 模型版本 × 提示词版本）建议 ≥100 条；不足标「样本不足」。该数与评测集「300 条/版本」的总量口径分开计：总量不足先标「未达 D21 总量」，不得判合格 | 周报与版本对比 |
| 阈值与策略调优 | 置信度分布、改判原因分布、边界样本占比 | 每场景建议 ≥500 条再谈调阈值 | 调优建议（不自动执行） |
| 词库/规则候选 | 误判/漏判样本按原因标签聚类 | 同类 ≥20 条形成候选 | 候选池条目 |
| 模型灰度评估 | 新旧版本在固定评测集上的差异 | 每版本建议 ≥300 条固定样本 | 放量/回退建议 |
| 运营看板与告警 | 采纳率周环比、误判率、过期任务数 | 实时/每日 | 告警与值班工单 |

> 上述样本量用途不同、不可互相替代：**评测集 300 条/版本**（D21）是模型灰度与质量报告的固定样本总量；**调阈值需该场景 ≥500 条反馈记录**是调整置信度或阈值的门槛。原文「最终由 D21 的评测基线统一」仅指两者都按 D21 的基线定义校准，不是把 500 降为 300。

告警建议：采纳率周环比下滑表示模型/提示词疑似退化，误判率高于基线表示口径漂移，过期任务占比偏高表示人工积压——以上是业务含义。**具体阈值、统计窗口、校准责任方与状态以 [AI-Architecture.md](../Architecture/AI-Architecture.md) 的「告警阈值建议」为唯一出处**（见清单索引 Q72），本节不重复数值，避免两处漂移；阈值未校准前以 review 已配置的积压值（存疑 50 条、DLQ 100 条）为准。

**F13.4 回流动作（怎么真正闭起来）**

1. 每日聚合：按场景与版本生成候选集，标注来源记录。
2. 候选分两类：**误判**（AI 判违规、人工判通过）→ 词库/规则候选；**漏判**（AI 判通过、人工判违规）→ 规则/提示词候选。
3. 人工确认：由审核运营负责人确认；词库变更沿用现有词库版本发布流程；提示词变更由算法值班评估 + 审核运营负责人审批（V9 定档 2026-11-08）；每次确认留操作人、时间、依据样本。
4. 生效方式：词库走版本发布；提示词/阈值先影子运行或小比例灰度，采纳率与误判率不劣化再放量。
5. 验证防反向污染：调优样本与验证样本分开；用固定评测集回归，避免「用同一批样本调完再自证」。
6. 明确不做：不自动训练、不自动调阈值、不自动换模型；系统只产出候选集与建议。

**F13.5 与 F22、F21 的分工**

- **与 F22**：共用一份记录实体，用 `record_type` 区分「机审反馈」与「生成质量」。审核字段（AI 建议、人工结论、是否一致）两边通用；F22 额外记录生成质量评分与错误类型。**不做两套表**，避免同一内容两处口径。
- **与 F21**：F21 发现卡死或超时任务时，向 F13 写一条「操作类型=过期」的记录：人工结论为空、`是否一致=不可比`，只进入积压与时效统计，**不进入准确率分母**，避免把「没人看」算成「判错了」。

**业务规则**：

- AI 建议与人工结论必须分开留痕，否则无法计算采纳率。
- 误判样本要能追溯到具体内容、场景与模型/提示词/词库版本。
- 词库误报（DFA 命中争议）归 review 的词库治理，不计入 AI 误判率，避免两套口径互相污染。
- 系统只出证据与建议；调阈值、换模型始终由人决定。
- 反馈记录只增不改；「最终生效」标记可回填，历史不改写。

### F14 AI 能力运营配置与预算管控

| 项 | 内容 |
| --- | --- |
| 批次/状态 | 第一批 P0（基础开关），持续增强 |
| 输入 | 场景（机审文本/机审图片/摘要/标签/问答）、模型版本、配额、预算额度 |
| 输出 | 开关生效、配额扣减、超额拒绝、预算告警、灰度比例 |
| 触发时机 | 运营配置变更；每次调用 |
| 可见结果 | 运营后台配置与用量；用户超额提示；作者看到某功能「暂不可用」 |
| 不做什么 | 不允许通过配置绕过内容出站边界；不允许关闭机审不可用告警 |

**业务规则**：

- 场景级独立开关：可停生成式而保留机审，可停图片而保留文本。
- 预算分两级：预警线告警；上限线停生成式，机审预算打满则转全量人工并告警，**不降低机审判定频率**；不得停掉「机审不可用」告警。
- 配额按用户与场景分别计量；VIP 与普通用户规则不同。
- 配额扣减：先按「用户 + 场景 + 周期」原子预扣，调用失败或未产生结果时退还；同一 `requestId` 只扣一次；并发请求以预扣成功为准，超额后到者直接拒绝。
- 模型版本切换支持按比例灰度，可随时回退。
- **配额规则（D5，已定 2026-11-08）**：普通用户先按日低配额，按用户等级逐级放开；VIP 设高额度上限，不设不限量；叠加生成预算科目（与机审预算分账，见 D15），达预警线告警、达上限停生成。
- 任何配置变更都要留痕：谁、何时、改了什么。

## 十二、补充规则与口径修正

1. **口径修正（重要）**：原 §4.1 写「已发布内容被编辑后再次送审」不准确。实际 `status=2` 禁改正文/标题/配图，改正文只能软删旧文重新发布；「陈旧性防线」真正处理的是待审期间内容变化、结论迟到，而不是已发布内容反复送审。
2. **词库与模型的分工**：DFA 同步闸门负责「命中词」的硬拦截与观察留痕；AI 负责「语义风险」判定。文本结论的版本必须带词库版本，换库不复用；词库误报走 review 的误报入口，不计入 AI 误判率。
3. **评论与私信现状**：content 侧对 bizType=2 的审核结论只挂起留痕，不驱动评论状态；评论/私信的实际展示由 social 决定，而 social 当前未启用。AI 判定能力本身不受影响，但结论暂时没有在线消费方。
4. **摘要现状**：摘要字段 ≤500 字、独立过 DFA 闸门、不参与正文指纹；AI 摘要生成必须遵守同一口径。
5. **「回查失败不放行」是跨模块硬规则**：申诉恢复前回查处罚态失败（异常、业务码非 0、空数据）一律不放行并重试，不允许把「查不到」当成「没处罚」；重试上限 3 次 / 总时长 1 小时，耗尽后进入「复核中」收口（V1/V2，见 F10 业务规则）。

### 15.4 补充功能项（F18–F22）

#### F18 发布入口全覆盖与送审守卫

| 项 | 内容 |
| --- | --- |
| 批次/状态 | 第一批 P0（与 F1/F2 同批） |
| 输入 | 所有会改变内容可见性的入口：正常发布、编辑后重发、批量导入、定时发布、迁移/复制、草稿箱转发布 |
| 输出 | 每个入口都产生送审任务；缺送审的入口被拦截并告警，内容停在「未提交」态，不进入审核中 |
| 触发时机 | 任一发布类操作提交时 |
| 可见结果 | 作者不额外看到审核细节，但被拦截时能看到「未提交成功」及可读原因；漏送审的内容不会出现在读者侧 |
| 不做什么 | 不替业务判断是否免审；不对历史已发布内容做全量回溯（回溯属 F19） |

**为什么必须补**：当前只覆盖「发布/配图复审」主路径，批量导入与定时发布没有明确送审动作。只要有一个入口绕过，前面所有判定与验收都失效。
**不补的后果**：出现「批量导入的文章未经机审直接可见」，且事后无法从审核记录反查。

**拦截后如何补送审**：被拦截的内容保持「未提交」，作者修正后重新提交即重新走该入口的送审守卫；批量/定时入口由发起方在任务创建时补送审任务，补送审成功前不得置为可见。

#### F19 存量结论重判与版本迁移

| 项 | 内容 |
| --- | --- |
| 批次/状态 | 第二批 P1 |
| 输入 | 模型版本、提示词版本、词库版本变更事件；存量结论 |
| 输出 | 过期标记（仅表示「不再参与免审复用」，仍作历史证据）；抽样或全量重判任务；重判差异报告 |
| 触发时机 | 版本变更发布时；按周期抽样 |
| 可见结果 | 运营看到「旧版本结论」占比与重判差异；作者通常无感（仅高风险样本可能改判） |
| 不做什么 | 不自动批量下架；不自动用新结论覆盖旧处罚，改判仍走人工/申诉 |

**为什么必须补**：F12 只解决「新内容不复用旧结论」，没解决「已落库的旧结论怎么办」。
**不补的后果**：换模型后平台同时存在两套判定口径，误判追溯与效果评估全部失真。

**过期 ≠ 作废**：过期标记由 F19 在版本变更事件写入，表示旧结论不参与免审复用与新的聚合判定；旧结论本身继续按 §5.4 留存，作为申诉、审计与合规举证的历史证据。重判产出新结论后，旧结论只归档、不删除；过期标记不因重判完成而清除，随旧结论一起归档。

**两个触发源去重（见清单索引 Q59）**：重判任务键 = `内容指纹 + 目标版本`。版本变更全量/抽样重判与周期抽样命中同一内容时，同一任务键只建一次任务，已完成任务直接跳过；周期抽样只补「该目标版本尚未重判」的内容，不重复产出第二份结论。

**抽样参数（见清单索引 Q37）**：低风险层 10%，高风险层 100% 全量；周期按月 + 版本发布后 7 天内补跑（V7 定档 2026-11-08）。校准责任方同 [AI-Architecture.md](../Architecture/AI-Architecture.md) §11.3。

#### F20 审核结论通知与用户触达协同

| 项 | 内容 |
| --- | --- |
| 批次/状态 | 第一批 P0（跨模块补写） |
| 输入 | 机审/人工/申诉裁决结论；判定理由摘要 |
| 输出 | 作者可收到的状态通知（审核中、通过、驳回、恢复）与申诉入口 |
| 触发时机 | 结论落库后；申诉裁决后 |
| 可见结果 | 作者知道「为什么被拒、去哪里申诉」；读者侧无变化 |
| 不做什么 | AI 不直接发通知；通知渠道与模板由 notification 负责 |

**为什么必须补**：review 侧已经发布 `appeal.result` 等事件，但 AI 文档没有写结论通知这一环，导致「结论落地」只落到库、没落到人。
**不补的后果**：作者只看到内容消失，不知道原因与申诉路径，申诉量与会话投诉上升。

#### F21 审核链路对账与卡死任务清扫

| 项 | 内容 |
| --- | --- |
| 批次/状态 | 第一批 P0（稳定性兜底） |
| 输入 | 聚合未完成的文章、超时未裁决任务、隔离与解隔离状态不一致的文件 |
| 输出 | 对账报告；补发结论（以已到达的终局结论为准，缺失一路按存疑转人工）；补偿解隔离；超时任务升级告警 |
| 触发时机 | 定时扫描；关键事件缺失告警时 |
| 可见结果 | 运营看到积压与不一致清单；作者不会长期停在「审核中」 |
| 不做什么 | 不替人做裁决；不自动改判，只补流程动作 |

**为什么必须补**：文章结论依赖文本与配图两路聚合，任何一路丢失都会造成「永久审核中」；申诉恢复也可能是「文章成功、文件失败」。
**不补的后果**：状态卡死只能靠用户投诉发现，且无法区分「真的在审」与「链路丢了」。

**补发与互斥规则**：补发必须携带任务幂等键，由 content / file 侧以 CAS 拒绝重复回写；补发与正常消费同时到达时，以结论序号大者为准（见 F10「先后守卫」），较小者记审计日志后丢弃。

#### F22 生成质量评测与人工抽检

| 项 | 内容 |
| --- | --- |
| 批次/状态 | 第二批 P1（D4 未来开启自动写入的前置） |
| 输入 | 摘要、标签、问答、写作辅助的生成结果；人工评测样本 |
| 输出 | 质量指标与错误分类、场景级准确率；是否具备自动写入条件的结论；**质量合格线（V10）**：可用性 ≥4/5 占比 ≥80%（初值待校准）、关键事实错误率 ≤1%、场景准确率不低于阶段 0 基线，三项全过才算合格 |
| 触发时机 | 上线前基线评测；上线后按周期抽检 |
| 可见结果 | 运营与产品看到质量报告；作者看到的是「建议」而不是「定稿」 |
| 不做什么 | 不自动判定「可以自动写入」；是否开启仍由 D4 的回退条件决定 |

**为什么必须补**：D4 已定「默认不自动写入」，但没有质量评测就无法判断何时可以进入下一阶段，也无法证明「建议态」是有效的。
**不补的后果**：AI 建议长期无法转正，或凭感觉转正后出现批量错误摘要。

**开启自动写入的决策组（见清单索引 Q46）**：D4 只写了「必须满足发布级闸门」这一前置。决策组按 V9 定档（2026-11-08）：产品负责人提议，审核运营 + 法务书面会签，附 D21 评测报告与 V10 合格线结论；未走完会签前，D4 维持「默认不自动写入」，不得由一线自行开启。

### 15.6 必须补写的规则（不新增功能项）

1. **预算分账与保护**：机审预算独立且优先；机审预算打满时降级为「全量人工 + 告警」，不得静默放行；生成预算打满只停生成式，不停机审。
2. **闸门执行方**：DFA 闸门由调用方（content/review）执行，AI 只返回文本与标识；闸门不可用时，生成结果不得落库或展示。
3. **通知边界**：review 发布结论事件，notification 消费并触达作者；AI 只提供判定理由摘要，不直接发通知。
4. **评论/私信边界**：social 未启用期间结论只留痕；启用前必须补齐消费方，否则不得对外宣称「评论已机审」。
5. **摘要/标签变更边界**：两者不进入正文指纹，不触发正文重审；但标签变更需过词闸门，摘要变更需过闸门后才可展示。

### 16.2 实施前置（不是决策缺口）

以下事项已不需要拍板，但需要外部条件或工程投入才能落地：

1. **AI 计量与用途打标（D15 的前置）**：现有代码没有 Token/成本计量，只有全站 QPS 与 per-user 限流；要分账，先在 AI 调用入口按用途打标，再分别累计与限额。
2. **固定评测集与标注人力（D16、D21、D24 的前置）**：没有评测集，抽样重判与质量基线都无法执行。
3. **结论版本标识（D16 的前置）**：模型/提示词/词库版本必须随结论落库，否则无法标记过期。
4. **反馈记录实体与工作台强校验（D22、D23 的前置）**：没有表和强校验，标签强制与保留期都无从谈起。
5. **审核预算科目（D15 的前置）**：财务不设两个科目，分账只是文档口径。
6. **本地图片模型与算力（D2、F2、F11 的前置）**：本地模型文件缺失、推理算力未保障；不可用时按既定降级保持待审并全量转人工，不回退云 API（见 9.1 的 D2 硬冲突与本清单 3.1）。

#### 16.3.3 V1 与 V2 成对约束

单改一个必然错配：只加 V1 次数 → 次数没用完时长已到，提前转人工；只加 V2 时长 → 时长没到次数已用完，少重试即转人工。两处必须同批改，并重算退避间隔与耗尽后的「复核中」收口时点。

#### 16.3.4 V8 与 V5 同一次工程改造

两者都依赖「AI 调用入口的按用途计量 + Redis 计数」：V8 算花多少，V5 判断坏了多久。分开做会重复改同一批调用点、重复定义用途枚举与 Redis 键。要求同一迭代完成，共用一套埋点与键命名（口径见 §5.3 五类用途）。

#### 16.3.5 V3 定档与 V6 抽样范围（2026-11-08）

V3（文本机审出站边界，对应 Q63）已于 2026-11-08 拍板：**私信内容只做机器判定；未公开内容按公开内容处理（与外发同等对待）**；用户已删除内容仍不外发。定档后 V6 的审计抽样范围从「仅生成式与问答外发」扩展为**文本机审全量外发**，人力需求同步上调，扩量后首月需按实际外发量核算 1% 是否超过 100 条。

这项决策的前提假设不是默认成立：法务未书面确认前，私信与未公开内容只走本地模型或转人工（见 §5.4）。翻案条件为法务否定或监管要求变化，回退时不改 V6 的抽样方法，只缩回抽样范围。

## 附录：术语

| 术语 | 含义 |
| --- | --- |
| 三分态 | 机审结论只有三种：通过、违规、存疑。存疑必须转人工，不存在「默认通过」 |
| 存疑 | 机审结论之一，等价于「待人工」「待审」；正文统一用「存疑」，避免三种叫法混用 |
| 待审（`safe_flag=2`） | file 侧图片状态字段取值，表示尚未有结论、等待判定；与 content.status=1「审核中」不是同一个字段 |
| 同步闸门 | 宿主服务在提交动作内本地执行的敏感词检查，毫秒级，不依赖 AI 可用性 |
| 自动通过 | 机审判为「通过」后由 review 直接放行，未经人工 |
| 免审 | 内容未变且上次已通过时复用结论直接放行；但配图仍必须复审。与「自动通过」的区别是复用旧结论而非重新判定 |
| 放行 | 结论为通过且已写回业务状态后的可见结果，不单独作为一种结论类型 |
| 隔离 | 违规图片退出业务可用状态但保留存储，申诉成功可恢复 |
| 下架 | 已发布内容因违规退出可见，与图片隔离是两件事；下架不等于删除存储 |
| 软删 | 超过保留期后标记删除但保留恢复期，期满才物理删除；与「下架」「隔离」不同 |
| 拒传名单 | 违规图片的短期上传黑名单，命中即拒传；申诉平反后移除 |
| 原因码 | 违规结论对应的风险类别代码，用户可见理由由它映射，不透出模型原文 |
| 置信度 | 模型对结论的把握程度；缺失时标「不可用」，不参与阈值分析 |
| 过期标记 | 版本变更后给旧结论打的标记：不参与免审复用，但仍作历史证据 |
| 反馈记录 | F13 的追加型记录，一次人工操作一条，用于效果评估与归因 |
| 建议态 | AI 生成结果只展示、不落库，需作者确认后才生效 |
| 引用 | 问答回答中指向站内文章的出处卡片，必须可打开且随下架失效 |
| 出站 | 内容被发送到站外模型服务；默认从严管控 |

> **正文用词约定（见清单索引 Q21）**：机审结论统一写「存疑」，「待人工」只在描述人工动作时使用，「待审」专指 `safe_flag=2`；结论为通过时的动作统一写「放行」，复用旧结论时写「免审」；图片状态统一写「隔离」，到期处理统一写「软删」，已发布文章退出可见统一写「下架」。三组混用是历史写法，新增内容按本约定执行。
